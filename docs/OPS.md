# UPayNow 部署运维

**简体中文** | [English](OPS.en.md)

## 启动和停机

使用独立服务账户、权限受控的本地持久存储，并保持一个数据目录只有一个写入实例。先按[安装说明](INSTALLATION.md)构建应用并配置 HTTPS，再将运行进程交给服务管理器。可参考 [systemd 示例](examples/upaynow.service)；修改路径、账户、环境文件后在测试机验证，不要直接覆盖现有服务。升级时在切换前完成构建，不要把重新下载依赖或编译放进每次自动重启。首次使用新锁机制前，先停掉使用同一数据目录的旧版实例。

自动恢复仅适用于支持的 Linux 本地文件系统（ext、XFS、Btrfs 或 tmpfs）、可用的系统 flock，以及同一次系统启动和同一个 PID 命名空间。生产数据不要放在重启会丢失的 tmpfs 上。系统重启前留下的锁、旧版锁或无法核实的锁都需要人工确认；不要删除或替换持久的 `owner.guard`。

正常停机发送 SIGTERM，并等待进程退出再维护数据。进程重复启动失败时，先查看服务日志、磁盘空间和状态目录权限。不能确认没有其他写入者时，不要删除锁文件或并行启动副本。自动重启不是高可用，不要让两个实例处理同一批商城订单。

## 监控和排障

监控两层：从外部检查 HTTPS 可达性和进程存活，从商户侧检查每条链的扫描进度及付款通知队列。公开的 `/health` 不能替代业务监控，成功响应不证明已经识别付款或通知了商城。服务完全退出时本身不能发告警，进程掉线和证书到期需要外部监控补上。

商户可在已登录后台的同一来源访问 `GET /api/ops/status`。正常返回 200，检测到异常返回 503，未登录返回 401。它按部署汇总扫描和回调状态，不需要给外部监控签发商户 API 密钥。

生产进程每 15 秒检查一次，异常首次出现写入 `upay.ops.alert`，恢复写入 `upay.ops.clear`，持续同一异常不重复写入。将标准错误交给 journald 或本地日志监控；默认不发送 Telegram、邮件或其他外部通知。默认阈值包括 60 秒未完成一次健康扫描、落后至少 20 个区块、至少 25 个待发通知，或任一通知等待超过 120 秒。空白、尚未配置的实例不会因此告警。

优先处理持续扫描错误、扫描落后、通知长时间待发送、失败及需人工对账。涉及 EPay 时，按[接入指南](EPAY.md)用订单号核对链上到账、UPayNow 和 New API 的充值记录；已扣款但未充值时，不要批量重发或回滚一侧数据库。日志和外部监控只收集诊断所需的信息，不记录密钥、签名、完整回调地址或顾客数据。

## 备份、恢复和升级

按[加密备份与隔离恢复核验](OPS-BACKUP.md)操作。当前工具只在停写维护窗口执行，不自带生产定时任务。

备份 UPayNow 完整状态，包含根目录和每套部署的数据库与配置；不要只复制正在写入的单个 SQLite 文件。New API 账本单独备份，固定版本和外部部署配置也要有独立备份。备份加密，解密材料与备份文件分开管理。定期在隔离机器解密并核验，恢复演练不得对外发送付款通知或使用正在运行的实例目录。

恢复到旧快照前应暂停新单，核对快照之后的付款、发货和通知，确认没有时间窗口遗漏，再恢复业务。不要用“应用能启动”代替账目一致性检查。完整流程见[商户操作手册](OPERATIONS.md#65-完整一致性备份与安全恢复)。
