# New API EPay (optional)

[简体中文](EPAY.md) | **English**

UPayNow provides an **EPay MD5 web top-up adapter for New API `v1.0.0-rc.51`**. `/epay/submit.php` accepts only signed orders in that mode and notifies New API to credit the account once the on-chain payment is confirmed. It does not deploy contracts, sign on the merchant's behalf, change the existing API, or change collection for per-order addresses. It is not a general-purpose EPay gateway: RSA, `mapi.php`, refunds, payouts, and a general EPay-client query API are not supported.

See the target protocol in [New API's order and notification code](https://github.com/QuantumNous/new-api/blob/v1.0.0-rc.51/controller/topup.go#L271-L476) and [go-epay v0.0.6](https://github.com/Calcium-Ion/go-epay/tree/v0.0.6). Repository tests exercise a mock token transfer on a local EVM chain, on-chain scanning, and a simulated New API peer. They do not test a full New API deployment or mainnet. After building, reproduce them with `node --test backend/test/epay.test.cjs`.

## Configuration

1. Use the existing UPayNow workflow to configure and verify the deployment, payout wallet, token contract, chain ID, and required confirmations. The default deployment is `legacy`. For a separate deployment in the multichain dashboard, get its ID from `GET /api/deployments`. Verify that the HTTPS reverse proxy works and preserves the Host header, and that `UPAY_PUBLIC_ORIGIN` is set. Expose only the required checkout paths; do not expose the admin API as a top-up endpoint.
2. Confirm you are authorized to enable this payment method in New API and complete its payment compliance acknowledgment. Select **MD5** and enter `https://your-upaynow-domain/epay` as the gateway URL, without `submit.php`. Use the same PID and independent random secret as in UPayNow. Add a custom payment method with type `usdt` and a display name such as “USDT on-chain payment.” Do not label it as Alipay or imply that it processes Alipay payments.
3. Set these environment variables in the UPayNow service process, then restart it. An example environment file is not automatically loaded as dotenv. **Do not commit or log real secrets** or reuse them across gateways. MD5 is required for compatibility with this legacy protocol and is not recommended for new protocols.

   | Variable | Meaning |
   | --- | --- |
   | `UPAY_EPAY_ENABLED=1` | Explicitly enable the endpoint. It remains closed if unset or set to `0`. |
   | `UPAY_EPAY_DEPLOYMENT_ID` | Bind to one UPayNow deployment. Defaults to `legacy`. |
   | `UPAY_EPAY_PID` / `UPAY_EPAY_KEY` | Merchant ID and a high-entropy secret of at least 32 characters (e.g. generate with `openssl rand -hex 32`). |
   | `UPAY_EPAY_TYPE` | Only `usdt` is supported; it is also the default. |
   | `UPAY_EPAY_TOKEN` | Verified USDT contract address on the selected deployment. Do not rely on the token symbol. |
   | `UPAY_EPAY_PRICE_CURRENCY=USDT` | Required. The administrator confirms that the actual `money` field sent by the store is denominated in USDT. Fiat or exchange-rate configuration is not accepted. |
   | `UPAY_EPAY_NOTIFY_URL` | Actual New API notification URL, typically `https://new-api.example.com/api/user/epay/notify`. No query string. |
   | `UPAY_EPAY_RETURN_URL` | Actual New API return URL, typically `https://new-api.example.com/usage-logs`. |

   Both URLs must be complete HTTPS URLs and exactly match the values signed by New API. New API strips the trailing slash from `ServerAddress` and appends `/usage-logs` for the return URL. It uses `CustomCallbackAddress` (or `ServerAddress` if unset) and appends `/api/user/epay/notify` for notifications. The two hosts can differ. Notifications go only to the pinned URL: every DNS result must be a public IP, connections are pinned to a verified IP, and redirects are not followed. Configure the HTTPS proxy so access logs do not retain payment form and signature parameters; restrict access to New API's own payment logs as well. The deployment ID, chain/Factory, PID, token, method, and three URLs are bound to the database at first enablement. Do not change them in place to rewrite or bypass historical orders. Before key rotation, pause new orders, resolve in-flight orders, and synchronize both sides.
4. First configure the actual New API checkout price for this top-up method in USDT. Changing the currency symbol on screen is not enough: the legacy protocol has no currency field, so UPayNow cannot infer the upstream currency from the amount. Verify an order with a valueless token in an isolated environment. For example, if the store price is 10.00 USDT, the signed request's `money` must be `10.00` and UPayNow must show 10 USDT due. Do not enable this endpoint for orders priced in CNY or USD. Verify the recipient address, the required confirmations, the actual credit in New API, and that a duplicate notification does not change the credited amount. Do not use it for real top-ups until you have verified New API's actual ledger.

## Operation and recovery

- The isolated combination of PID and `out_trade_no` is bound to the amount and quote from the first signed request. The amount due is exactly the supplied two-decimal USDT value; no exchange rate is retrieved or applied. The amount and order ID persist, repeated submissions return the original address, and an expired order cannot be reactivated with the same ID. Orders expire after 30 minutes by default. A successful submission redirects only to the local checkout. The native scanner sends a notification only after it confirms payment. Payment confirmation is not proof of top-up credit. When New API returns a success response, checkout displays “Return to top-up site.”
- New API notifications are signed form POSTs. Delivery is recorded only when New API returns HTTP 2xx and a body of exactly `success`. The adapter sends at most eight attempts, using the same merchant order ID and platform transaction ID every time. Deduplication relies on the ledger transaction in this New API version, not on exactly-once HTTP delivery. An unknown outcome at the limit goes to `RECONCILE`, with no further send after a restart. Keep background on-chain polling enabled.
- If a chain reorganization invalidates a confirmed payment before a successful-payment notification is attempted, the notification is canceled. If delivery has been attempted (even if the acknowledgment was lost) or acknowledged, the status becomes `RECONCILE`; even if the payment reconfirms, the adapter does not automatically resend the notification or deduct credit. The merchant must compare on-chain records, the New API balance, and top-up records, then resolve manually. Confirmations do not eliminate reorganization risk.
- Use an existing merchant session or API key to query `GET /api/epay/orders?out_trade_no=...` (one bound PID/deployment; an external PID is not accepted). `GET /api/epay/orders?state=RECONCILE` lists the latest 100 orders requiring manual reconciliation. Main states are `WAITING` (awaiting confirmation), `PENDING` (awaiting delivery), `DELIVERED` (New API acknowledged), `SUPPRESSED` (canceled before sending), `FAILED` (retries exhausted), and `RECONCILE` (manual reconciliation required). `attempts` counts potentially sent requests; `preflightFailures` records failures before sending, such as DNS errors. The backend uses bounded exponential backoff. For `FAILED`, first verify payment receipt, New API credit, and callback availability, then handle the case in New API's merchant dashboard. The adapter does not provide a forced resend or automatic reversal. Back up the state database and the New API ledger independently; do not delete or roll back one side's database as a retry mechanism.

### Review the callback queue

In the UPayNow merchant console, open **Payment webhooks → EPay callbacks and reconciliation** on the deployment bound to EPay. Filter for **Needs manual reconciliation**, **Callback retries exhausted**, or **Awaiting callback delivery**, and page through the results. The waiting queue is read-only. Operational counts still count all outstanding delivery exceptions, even if an operator records a review.

For exceptions, copy the full **Store order number** (`out_trade_no`). In the administrator top-up history on the same New API instance, search for the full number and confirm the exact match. Use **View the original UPayNow order** to find the chain receipt. Compare the token, amount, and current canonical chain evidence separately from the New API top-up status. On the pinned New API version, an exact successful top-up record is receiving-side credit evidence, not proof that payment remains canonical. A pending or missing match is not permission to resend, credit or reverse anything.

Use **Record manual review** to record both findings. This adds a dated entry to the order's review history without changing the payment, delivery state, or store balance. A newer reversal or change in the native payment evidence makes the previous review stale. The history records the admin session or API credential channel, not the identity of an individual sharing access.

API clients can use the deployment-scoped `GET /api/epay/operations?state=FAILED` (or `RECONCILE` / `PENDING`) and `GET /api/epay/operations/reviews?out_trade_no=...`. Send the EPay deployment in `X-Upay-Deployment`. For the next page add `before` with the returned `nextBefore`; `null` means there are no more rows. The default limit is 25 and the maximum is 100. This is a live queue; state changes may move items between filters. The existing `/api/epay/orders` endpoints are unchanged.
