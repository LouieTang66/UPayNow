# UPayNow 商户操作手册

**简体中文** | [English](OPERATIONS.en.md)

安装前先读[安装与 HTTPS 部署](INSTALLATION.md)，其他资料见[文档索引](README.md)。

## 阅读顺序

1. 首次使用：设置密码、保存恢复密钥、准备钱包、理解当前部署。
2. 添加网络与部署收款合约：使用内置网络/RPC 预设，部署或导入自己的合约。
3. 收款与订单管理：接入商城、查看订单、判断付款和通知结果。
4. 正常归集：单笔或批量归集，使用电脑或手机钱包确认。
5. 错币与错链找回：先判断能否找回，再执行对应的恢复操作。
6. 异常处理与日常维护：排查、改密、备份、恢复、升级与迁移。

每项操作按“适用情况 → 操作前准备 → 在哪里操作 → 钱包签名与 Gas → 成功结果 → 异常处理”的顺序说明。

## 1. 首次使用

### 1.1 使用前先准备什么

- UPayNow 服务已安装并启动；首次安装的基础要求为 Node.js 22.19 或更新的兼容版本、npm 及持久化数据目录。由部署者完成服务器配置，不需要另外启动一个前端服务。
- 确认正在访问自己的实例。本机默认地址为 `http://127.0.0.1:8790`；若部署者改过端口，或使用服务器 HTTPS 地址，应使用实际入口，不能照搬别人的管理地址。
- 准备密码管理器或其他受保护的保存位置，用于保存密码、恢复密钥和商城凭据，不要存入公开仓库或分享截图。
- 准备能由自己控制并签名的兼容 EVM 钱包。连接钱包时无需向 UPayNow 输入私钥或助记词。

新实例没有商户自己的合约和订单，这是正常状态。系统内置已开放网络及 RPC 预设，不等于已经替你部署了商户收款合约。

### 1.2 第一次设置登录密码

**适用情况**：打开自己的新实例，页面显示“首次设置登录密码”。

**操作前准备**：取得这个实例当前的恢复密钥。它来自该实例的数据目录，不是钱包助记词、商城 API 凭据，也不是其他测试实例的密钥。

如果由他人替你部署，应通过可信方式取得本实例的恢复密钥。自己部署时，可在服务器或本机的项目根目录运行以下只读取回命令，将示例路径替换为实际完整数据根目录：

```sh
npm run recovery-key -- "/实际数据根目录"
```

该命令会在终端输出恢复密钥，不要把输出放进聊天、录屏或共享日志。macOS / Windows 可改用只复制到本机剪贴板、不显示明文的方式：

```sh
npm run recovery-key -- --copy "/实际数据根目录"
```

Linux 当前不支持该 `--copy` 选项。通过 SSH 在远端执行复制命令，也不等于复制到了你电脑的剪贴板。命令不传目录时读取进程环境变量 `UPAY_DATA_DIR`；未设置时读取项目的 `backend/state/`。有多套实例时建议显式传入目录，避免拿错密钥。

**在哪里操作**：

1. 在首次设密页填写“现有恢复密钥”。
2. 填写“新密码”和“确认新密码”。密码须为 12–128 个字符，不能全为空白；首尾空格会保留，不会自动帮你去掉。
3. 点击“设置密码并生成新恢复密钥”。
4. 成功后页面显示“密码已设置，请保存新恢复密钥”。点击“复制”或“下载备份”，妥善保存新的恢复密钥。
5. 勾选“我已妥善保存新恢复密钥”，点击“已保存，返回密码登录”。
6. 使用刚设置的密码登录。

**钱包签名与 Gas**：以上都是实例认证操作，不连接钱包，不发链上交易，不花 Gas。

**成功结果**：密码可以登录；原先用于设密的恢复密钥已被新密钥替代。无商户部署时会看到“开始使用 UPayNow”，可以点击“添加链”，或先进入“设置”。

**异常处理**：

- “两次输入的新密码不一致”：重新核对两个密码框，注意空格和输入法。
- 恢复密钥无效：先核对当前浏览器访问的实例和命令读取的数据目录是否一致，并重新取回当前密钥；不要删除 `auth.json` 来绕过校验。
- 取回工具报 `RECOVERY_KEY_UNAVAILABLE`：确认这套服务已启动并生成认证文件、目录正确、当前系统账户有读取权限。
- 点击设密后断网，没看到新密钥：先尝试使用新密码登录；成功后按 1.4 重新备份恢复密钥，不要因为响应丢失就删文件重置实例。

### 1.3 三种凭据不要混用

| 凭据 | 用途 | 不应该怎么用 |
| --- | --- | --- |
| 登录密码 | 日常进入商户后台；修改密码或查看敏感凭据时再次验证 | 不交给顾客网页，不当商城 API 凭据 |
| 恢复密钥 | 首次设置密码、忘记密码时重置 | 不能直接登录，也不能作为业务 API 的 Bearer 凭据 |
| 独立 API 凭据 | 商城服务器调用 UPayNow 的业务接口 | 不交给顾客浏览器，不放前端 JavaScript，不当登录密码 |

API 凭据当前并非只有创建订单权限，仍具有广泛业务管理权限，应按敏感服务端密钥保管。改密或重置密码不会自动更换 API 凭据；不能认为“修改了密码，泄露的 API 凭据就安全了”。

### 1.4 登录后再次备份恢复密钥、查看 API 凭据

**适用情况**：已经登录，要重新保存凭据，或为商城接入准备 API 凭据。

**操作前准备**：当前登录密码，以及安全的保存位置。

**在哪里操作**：

- 备份恢复密钥：进入“设置” → “登录会话” → “备份恢复密钥”，填写“当前密码”，点击“验证并查看”。
- 查看商城凭据：进入“设置” → “独立 API 凭据” → “验证密码并查看 API 凭据”，填写“当前密码”，点击“验证并查看”。
- 在弹窗里使用“复制”或“下载备份”，保存后点击“关闭”。下载文件为明文敏感文件，不要留在共享下载目录或随手转发。

**钱包签名与 Gas**：不需要钱包，不发交易，不花 Gas。

**成功结果**：弹窗显示所选的当前凭据。查看、复制和下载本身不会轮换凭据；关闭弹窗会清除页面中的临时显示，不会清除已经复制的剪贴板或已经下载的文件。

**异常处理**：当前密码输错时，重新填写正确密码；若登录会话失效则重新登录。剪贴板复制失败时可手动选择保存或使用下载备份，不要为了复制密钥向陌生网站提交内容。

### 1.5 准备电脑钱包或手机钱包

**适用情况**：接下来要部署商户合约或执行资金归集。

**操作前准备**：确认钱包由自己长期控制，准备目标网络的原生 Gas 币。新建当前同地址商户合约时，签名钱包必须与填写的固定收款钱包相同；不能使用无法由自己签名的交易所充值地址。收款钱包选定后，合约中的归集目标不能更换。

有三种使用方式，按自己的设备选择，不需要全部配置：

| 方式 | 准备与入口 | 是否需要 Reown Project ID |
| --- | --- | --- |
| 电脑浏览器钱包扩展 | 在后续部署或归集弹窗中选择浏览器钱包，并在扩展中授权账户/网络 | 不需要 |
| WalletConnect | 先在“设置” → “WalletConnect”填写自己的“Reown Project ID”并点击“保存”，再使用后续操作中的 WalletConnect 连接 | 需要自己申请的 32 位十六进制 Project ID |
| 手机专用部署/归集入口 | 在相应任务中生成手机入口，在手机钱包可访问页面的环境中打开，并核对当前操作 | 不需要 |

“设置”中的 WalletConnect 卡片是可选配置，不是所有商户都必须申请 ID 的前置步骤；Project ID 可以在配置链之前保存。手机专用入口与 WalletConnect 二维码是不同机制，不要混为一谈。具体手机打开方式和按钮在部署、归集章节分别说明。

**钱包签名与 Gas**：授权连接账户、切换网络、查看参数或打开二维码，本身不等于发送交易，也不等于部署或归集成功。只有核对当前操作并确认发送的链上交易才消耗 Gas。不要同意与本次操作无关的转账或授权。

**成功结果**：后续操作弹窗能读取正确账户和目标网络。钱包切错账户或网络时应先纠正，再核对参数，不要手动修改待签交易去绕过页面检查。

**异常处理**：未检测到扩展时，确认浏览器中有兼容的 EVM 钱包；WalletConnect 提示 Project ID 错误时，核对自己保存的 ID。连接超时或取消连接不代表已经发出部署/归集交易；若此前已在钱包确认过交易，则应查原任务和钱包记录，不能按“连接失败”推断可以重发。

### 1.6 Gas 应该准备在哪条链

Gas 由实际签名并发交易的钱包支付，必须放在执行该交易的网络上。仅有 USDT 等代币余额，或仅在另一条链上持有同名币，都不能支付当前链 Gas。

| 当前已开放网络 | Chain ID | 该网络用于支付 Gas 的原生币 |
| --- | --- | --- |
| BNB Smart Chain | 56 | BNB |
| Arbitrum One | 42161 | Arbitrum 网络上的 ETH |
| Base | 8453 | Base 网络上的 ETH |
| Plasma | 9745 | XPL |
| X Layer | 196 | OKB |
| BSC Testnet | 97 | 测试 BNB（tBNB） |
| Ethereum Sepolia | 11155111 | Sepolia 测试 ETH |

钱包应按交易预估准备充足 Gas，费用随网络和操作变化。找回错链资产时，需要的是资产实际所在目标链的 Gas，不是原订单链的 Gas。以上为网络列表和 Gas 对照，不代表任意代币都已经被你的商户合约支持。

### 1.7 理解顶部“当前部署”

**适用情况**：同一个后台管理多条链，或同一链上有不同部署，要确认自己正在查看哪套收款业务。

**操作前准备**：至少有一套已核验的商户部署；首次没有部署时，先完成第 2 章。

**在哪里操作**：通过后台顶部的部署选择框切换。每套部署对应自己的网络、收款合约、固定收款钱包、币种配置、订单与任务记录；不要只看网络名字，还要核对当前合约与部署 ID。

**钱包签名与 Gas**：切换后台当前部署不连接或切换你的链上资产，不发交易，不花 Gas。

**成功结果**：总览、订单、归集、付款通知和商城接入等页面显示所选部署的数据。切换不会停止其他部署扫描，也不会把原订单改到新合约，不会改变旧合约的收款钱包。

**异常处理**：

- 切换会丢弃尚未提交的部署相关表单草稿，例如测试订单输入；先确认无需继续该草稿。
- 已开始的归集/恢复操作绑定原部署，不能靠切换顶部选择框改变待签交易的目标。先完成或安全退出该操作；结果未知时保留原任务处理。
- 找不到某笔订单时，先检查当前部署是否选对，不要立即重建订单。
- 显示加载失败时先检查后台错误；不要删除历史部署、数据库或未完成任务来“修复”列表。

### 1.8 完成本章后的检查

- 已设置自己的登录密码，并能重新登录。
- 已保存首次设密后生成的新恢复密钥，知道旧恢复密钥已经失效。
- 分清密码、恢复密钥和 API 凭据；商城凭据只放服务器。
- 已选定自己使用的钱包方式；没有被要求上传私钥或助记词。
- 知道目标链需要哪种 Gas，以及“当前部署”只改变后台查看上下文。

下一步：添加网络并部署自己的商户收款合约。

## 2. 添加网络与部署收款合约

### 2.1 先分清“开放网络”和“添加自己的部署”

- **开放新网络**：由项目维护方核验该链的兼容性及公共部署入口，并加入已开放网络名单。
- **商户添加部署**：在已开放网络上，用自己的钱包部署固定收款钱包及币种列表对应的商户合约。

普通商户走第二种流程。添加一个 RPC 不会开放一条新链；不能通过修改 Chain ID 绕过名单。出现“公共入口未就绪”时应联系维护方，不要照旧技术文档自行签公共入口交易。

### 2.2 选择网络、填写商户参数

**适用情况**：首次接入一条收款网络，或为新的收款配置建立独立部署。

**操作前准备**：选好长期控制的固定收款钱包、准确的目标链代币合约地址（CA），并在同一个收款钱包中准备该链原生 Gas 币。当前新建部署使用跨链同地址方案，签名钱包必须与固定收款钱包一致。

**在哪里操作**：首次引导页点击“添加链”；已有部署时进入“链与合约”再点击“添加链”。在表单中：

| 字段 | 怎么填写 |
| --- | --- |
| 网络 | 从“请选择已开放网络”下拉框选择目标网络 |
| 显示名称 | 随网络自动填写，也可改成自己容易区分的名字 |
| Chain ID | 新建模式自动填写且只读，不需手动输入 |
| gas 原生币符号 | 自动填写且只读，不需手动输入 |
| RPC | 使用系统预设，无需手动填写；确需更换时才展开“高级：自定义 RPC（HTTPS）” |
| 固定收款钱包 payout | 填写自己能长期控制、并能用于本次签名的钱包地址；部署后不能改 |
| 支持的代币合约地址（每行一个） | 按目标链逐一核对完整 CA，一行一个，不填 USDT 等简称 |
| 付款确认数 | 默认 12；允许 1–256，按网络与业务要求核对，不把低确认数当成绝对安全 |

同名代币在不同链上通常有不同 CA。不要复制原链 USDT 的地址去另一条链使用，也不要把原生 Gas 币的零地址填成普通订单支持币种。

**钱包签名与 Gas**：填写和选择网络不发交易。自定义 RPC 必须为 HTTPS，不能在 URL 中嵌入用户名密码；带密钥的节点地址可能出现在记录中，不应随意截图分享。

**成功结果**：网络参数自动带入，固定钱包和币种信息完整，可以点击“验证参数”。

**异常处理**：已开放网络名单加载失败时，新建部署会禁用。关闭后重试或检查服务连接；不要手动拼请求绕过。RPC 校验失败先检查预设节点连通性，确有需要再使用高级节点设置。

### 2.3 验证、核对并用电脑钱包部署

**适用情况**：参数已填写完整，准备部署商户合约。

**操作前准备**：关闭其他未完成的钱包发送流程；确认固定收款钱包里有目标链 Gas。

**在哪里操作**：

1. 点击“验证参数”。后台读取链上信息、核验入口与配置，并生成部署记录；这一步不会发送交易。
2. 在“核对部署参数”中核对网络、固定收款钱包、支持币种完整 CA、精度、付款确认数和预期 Factory 地址。名称相同不代表 CA 正确。
3. 有错误时点击“返回修改”，修改后重新验证；不要在钱包里临时改交易来补救。
4. 点击“下一步：选择钱包”。
5. 使用扩展钱包时点击“部署商户合约”；使用 WalletConnect 时点击“WalletConnect”，并完成钱包连接授权。
6. 在“核对并确认部署”中核对网络、发送钱包、固定钱包、支持币种及“部署商户合约”阶段。
7. 点击“确认并交给钱包”，再在钱包中核对本次合约调用、网络、账户和费用，确认发送。
8. 等待后台取得回执、满足确认数并完成合约核验。

**钱包签名与 Gas**：连接钱包不是发交易；第 7 步才将本次部署交给钱包发送。签名者必须为固定收款钱包，由它支付目标链 Gas。钱包可能另行请求切换或添加网络，这不是第二笔部署交易。

**成功结果**：部署记录显示“部署成功 · 已加入”，详情提示“部署成功”；点击“切换到此部署”，并在“链与合约”核对实际 Factory、固定钱包和支持币种。拿到交易哈希、钱包显示已发送，不等于已登记可用部署。

**异常处理**：

- “该同地址商户合约已存在”：先核对已有合约，使用导入流程，不要重复部署。
- 钱包账户不是 payout：换到正确账户，不要改变待签交易的发送者字段强行继续。
- 入口不可用或公共入口未就绪：这是维护方需要处理的网络开放问题，不是要求商户再签一笔公共基础合约。
- 钱包已确认但页面超时：按 2.6 查原部署记录，不重新开始添加链。

### 2.4 改用手机钱包确认部署

**适用情况**：需要在手机钱包中签署同一笔商户部署，而不是使用电脑扩展。

**操作前准备**：已完成参数核对，手机钱包中有正确的固定收款账户及目标链 Gas；手机能访问 HTTPS 入口。

**在哪里操作**：在“选择钱包确认部署”中选择“手机钱包扫码”。首次准备临时入口时，程序可能自动从官方来源下载并校验所需组件；等待完成，不需要普通用户先手动安装 cloudflared。

入口就绪后，在手机钱包内置浏览器中打开页面，核对网络、固定钱包及支持币种，依次点击“连接钱包”及“确认部署（发送一次）”，再在钱包自己的确认界面核对并发送。电脑端可点击“查看部署记录”核对结果。页面里的完整入口链接是短期权限，不公开分享。

**钱包签名与 Gas**：二维码生成、打开页面不发交易；手机钱包中确认的交易由该签名账户支付 Gas。不需要 Reown Project ID。

**成功结果**：与电脑部署一致，以后台核验并加入部署列表为准。临时入口最长 5 分钟，倒计时不是交易确认倒计时。

**异常处理**：入口过期或点击“关闭入口”，不会取消已在钱包确认的交易；先查部署记录和原哈希。若仅入口组件下载/启动失败、还未交给钱包发送，可检查网络后重试或选择电脑钱包。组件校验失败时不要绕过校验。

### 2.5 导入已有的兼容收款合约

**适用情况**：商户合约已在链上存在，需要登记到当前实例，或恢复原部署的管理记录。

**操作前准备**：实际网络、原 Factory 地址、原固定收款钱包、按原链上顺序排列的完整支持币种列表及正确的扫描起始区块。只有名字或 ABI 相似不代表兼容。

**在哪里操作**：

1. 打开“添加链”，展开“高级／历史兼容：导入已有合约”。
2. 勾选“导入已有收款合约”。
3. 在“合约版本（仅导入）”选择真实版本：跨链同址合约（deterministic-v2），或旧版合约（legacy-v1，仅历史导入）。不要为了看到找回按钮把旧合约选成新版。
4. 核对网络与 RPC、固定钱包、币种列表，填写“已有 Factory 地址”。导入模式支持高级自定义网络参数，但仍需完整链上核验。
5. 在“起始扫描区块（可选）”填写不晚于需要识别的最早付款事件的正确区块，通常以合约实际部署区块为起点。填得太晚可能漏掉历史付款，太早可能增加扫描耗时。
6. 点击“验证并导入”，等待登记，再核对当前部署。

**钱包签名与 Gas**：导入只读取并核验已有合约，不发部署交易，不付部署 Gas。

**成功结果**：显示已导入，并切换到导入的部署。历史订单记录仍需来自原数据备份；只导入合约不等于恢复已丢失的订单数据库。

**异常处理**：版本、固定钱包或币种表不匹配时，回查真实链上信息，不要通过编辑数据库让检查通过。新建部署与历史导入的网络选择范围不同，不应把“可以导入”理解为“该网络已开放新建”。

### 2.6 部署超时、拒签或没拿到哈希

**适用情况**：窗口关闭、断网、钱包明确拒绝，或记录显示“结果未知”。

**操作前准备**：保留原部署记录 ID，查发送钱包的原交易。不要新建一条记录试着再发。

**在哪里操作**：进入“链与合约” → “部署记录”，选择原记录：

- 有原哈希：点击“登记原交易哈希”，核对后填入完整哈希，点击“登记并核验”。当前部署记录登记候选哈希后不能任意更换，不能试填顾客付款哈希或无关交易。
- 已登记哈希：使用“刷新状态”，等待链上回执、确认数和合约核验。
- 钱包明确显示已拒绝、确实未发送：才使用“登记明确拒签”，按弹窗确认。
- 仍为“已验证 · 未发送”，且确认此前没有交给钱包发送：可从原记录的“继续部署”恢复，不必重新建记录。

**钱包签名与 Gas**：登记哈希、刷新和登记拒签本身不发新交易，不花 Gas。重新唤起一条真正未发送的记录仍须再次核对，只有最终钱包发送才花 Gas。

**成功结果**：原记录继续核验并变为明确结果，保留完整历史。

**异常处理**：没有哈希不等于没发出，超时不等于拒签。误登记了部署哈希时，不要删除记录；先找真实创建交易和合约信息，核实后按兼容合约导入流程处理，必要时联系维护者。链上交易明确回滚后可以修正问题再部署，但不要把未知当回滚。新版部署是调用公共入口合约，钱包中可能显示合约调用而非“创建合约”；应找到原部署调用，不要仅凭旧提示文字寻找无接收地址的交易。

手机原入口在仍有效、没有已知哈希且符合原账户等限制时，可能出现“重新请求钱包确认”。这是显式重新唤起钱包，不是只读刷新，也不会取消旧的钱包弹窗或延长入口有效期。先排除原请求仍挂起或已经发送；有原哈希只登记，不同时确认旧、新两次请求。

### 2.7 为什么不能直接改钱包或币种

固定收款钱包和支持币种列表写入合约后不可修改；更换后台显示名称也不会改变链上资金去向。

当前同地址方案下，同一条链、同一固定收款钱包、同一部署版本对应同一个商户 Factory，不能仅换一份币种列表就再生成一套同版本合约。删除后台记录或反复点击部署都不能重置链上配置。

确需不同配置时，应先规划独立的新部署，例如使用另一个自己控制的固定收款钱包，并把新订单明确指向新部署；旧部署及历史订单继续保留处理。不要把旧订单的地址、Factory 或收款目标改到新部署上。

**完成本章后的检查**：正确选择网络；普通流程未要求手填 RPC；商户合约已核验登记；固定钱包、准确 CA、确认数和部署 ID 已核对；任何未知部署任务都保留原记录等待核实。

### 2.8 只修改后台显示名称

**适用情况**：为已登记部署补充容易区分的备注。

**操作前准备**：核对网络、Factory 和部署 ID，避免同名部署改错对象。

**在哪里操作**：进入“链与合约”，在对应部署点“编辑名称”。在“编辑部署名称”中填写“显示名称”，点击“保存”。名称不能为空，最多 128 个字符；允许重名，因此名称不能代替部署 ID。

**钱包签名与 Gas**：只改后台元数据，不需要钱包，也不花 Gas。

**成功结果**：提示“名称已更新”，列表和顶部选择器更新。

**异常处理**：保存失败保留原名称，检查错误后再试。改名不更换链上合约、固定收款钱包、币种或历史订单；不要用它假装已迁移网络。

## 3. 收款与订单管理

付款认定、付款通知、商城发货、资金归集是四件不同的事。不要把其中一项的成功当成其他项也已完成。

### 3.1 先把商城服务器接好

**适用情况：** 首次接入，或新增一套部署的收款方式。

**准备：** 完成部署核验，准备商城后端和可公开访问的收银台 HTTPS origin。顶部“当前管理的部署”选择正确网络与 Factory；同链也可能有多套部署，deploymentId 不是 Chain ID。进入“商城接入”，记录当前 deploymentId、准确币种 CA 和 decimals。

**在哪里点击填写：** 进入“设置 → 独立 API 凭据”，点“验证密码并查看 API 凭据”，输入“当前密码”，点“验证并查看”。取得凭据后交给负责商城后端的人员，通过服务器的秘密配置保存；关闭弹窗清空展示。不要把凭据写进顾客网页、App、公开仓库或普通日志，也不要用登录密码、恢复密钥替代。此凭据仍有广泛业务管理权限，并非仅能开单的最小权限 token；改密码或重置密码不会使它失效。

商城服务器调用 `POST /api/orders`，通过 HTTP Authorization 请求头使用独立 API 凭据进行 Bearer 认证，并用 `X-Upay-Deployment` 请求头指定部署 ID。填写 reference、token、amount、expiresInSeconds、webhookUrl。amount 用正数十进制字符串，不用浮点数或科学计数，精度不超过 decimals；有效期默认 1800 秒，允许 1–604800 秒。通知可以留空；启用时使用自己的 HTTPS 接收地址，由服务器运维将准确域名加入 `UPAY_WEBHOOK_HOSTS`，不接受私网目标或跳转。

**钱包/Gas：** 取得凭据、API 开单不要求商户钱包签名，不消耗链上 gas。

**成功看到什么：** API 返回真实订单 id、deploymentId、address、checkoutPath 等；商城保存这些字段及商户订单号、币种。正式订单由商城 API 创建，“订单”页没有日常开单按钮。当前“设置 → 辅助工具”确有“手动创建一笔订单”，定位是测试或补单，不替代正式商城流程，也不自动预留库存。

**异常：** 同一部署内 reference 幂等，参数完全一致才返回原订单，不同参数不能覆盖。请求超时先用相同 reference、相同参数重试或查单，不换新订单号绕开未知结果。部署不一致、CA 不支持或通知域名未允许时，修正配置再接入，不伪造成功订单。

### 3.2 把正确收银台交给顾客

**适用情况：** 商城已创建订单，顾客准备转账。

**准备：** 核对商品订单应付、部署、链和 CA，确认尚在有效期。使用开单返回的 checkoutPath 拼接公开 origin，不自行拼订单 UUID 当付款令牌。若从本机地址打开后台，复制出来的链接可能也是本机地址；不要把 127.0.0.1 链接交给远端顾客，正式业务应使用已配置的公共 HTTPS 入口。

**在哪里点击填写：** 商城向顾客展示收银台链接。人工协助时进入“订单”，在“搜索订单号、收款地址”中搜索，点击订单行，在详情“付款信息 → 收银台链接”复制。顾客打开后无需后台登录或连接网页钱包；按页面二维码或“复制收款地址”，在自己的钱包/提币界面选择相同链、相同 CA，填写该地址和应付金额。网络名相同或币种符号相同不足以替代 Chain ID、CA 核对。

**钱包/Gas：** 顾客在自己的钱包确认付款，承担该转账所需费用；商户此时无需签归集交易。交易所提币可能延迟，应为有效期留足时间。

**成功看到什么：** 收银台显示应付、网络/Chain ID、代币合约、已到账和已确认金额，状态自动刷新。金额足够但未达确认数时显示“已收到付款，正在等待网络确认”，不要再付一次。

**异常：** 链上转错币或错链不计入本订单付款，交人工核实，不按美元估值补足。若页面提示“到账状态可能有延迟”或“状态刷新暂时失败”，先查同步与原交易，不让顾客重复付款。链接找不到时核对完整链接和部署，不发送后台凭据来解决。

### 3.3 查单、欠款、分次与超额

**适用情况：** 日常对账、顾客称已付款，或订单金额与实际到账不一致。

**准备：** 取得商户订单号、原转账哈希及所属部署。先检查顶部是否“已同步”；“同步落后”“链上同步异常”或离线时，旧状态不能作为最终履约依据。

**在哪里点击填写：** 进入“订单”，可切“全部 / 已付足 / 进行中 / 需核实 / 已过期”，并按币种筛选。点击订单行，对比“应付”“已确认”“已检测（含未确认）”，查看“到账记录”里的金额、时间、交易哈希；“高级”可查订单 ID、CA、通知地址和状态版本。找不到先切换原部署。

**钱包/Gas：** 查单无需钱包、无需 gas；不要为了查付款而先归集。

**成功看到什么：** 后端按准确链上 Transfer、原订单 CA、区块时间与确认数累计，不要求一次转账付足：

- 待付款：尚无符合条件到账。
- 部分付款：有效期内累计不足，联系顾客在有效期内用同链同币补差；不同地址发出的同币到账也按订单地址累计。
- 确认中：计入范围的检测金额已足，但确认金额不足；耐心等待，不再催付整单。
- 已付足 / 已付足 · 超额：累计已确认金额达到 / 超过应付。超额部分需按商户退款策略人工对账；归集会带走该 CA 的全部余额，不会自动退差额。

**异常：** 过期时仍未足额会变“已过期”；另有未接受的迟付会提示“过期后到账”，但已足额或确认中的判定优先，不能仅凭一个状态名判断是否存在迟付款。有效期依据到账区块时间，不是截图或点击发送时间：有效期内足额到账、稍后才完成确认，仍可正常认单。归集后的零余额不代表未付；已归集也不代表付足。库存、预留、发货和退款由商城负责。

### 3.4 超时到账只能明确核实后接受

**适用情况：** 订单过期后顾客仍有到账，希望继续购买。

**准备：** 与顾客核对原链、CA、金额及哈希，商城先检查并预留库存；无库存转人工处理退款或其他安排，UPayNow 不替你锁库存或退款。

**在哪里点击填写：** 订单详情可看到“过期后到账”提示；当前订单抽屉没有“接受迟付”按钮。由商城后台以原认证和准确部署调用 `POST /api/orders/:id/accept-late-payment`，body 严格为 `{}`。服务先同步核验；首次接受要求订单已过期、存在原 CA 已确认迟付，且原币累计已确认足额，允许有效期内部分款加超时补款。

**钱包/Gas：** 接受是服务器账本操作，不发链上交易、不花 gas。

**成功看到什么：** 返回订单详情，核对 `paid === true`、`syncHealthy === true`、PAID/OVERPAID，以及 `latePaymentAccepted: true` 和接受记录。它只接受本次已确认到账快照，不永久批准未来迟付；原币种、金额、地址、到期时间不改。

**异常：** 同步未追平、迟付款未确认或总额不足不能强行改为已付。请求超时不能直接认定失败并释放库存，重试此幂等接口或查单核对。链重组撤回被接受到账时 paid 仍可能撤销，重复接受不会自动批准替代转账。未接受迟付虽可能被人工归集，归集本身也不等于接受该付款。

### 3.5 通知重试与安全履约

**适用情况：** 已付款但商城未更新，或通知失败。

**准备：** 商城保存所属部署的 `webhook.secret`，去掉末尾换行；各部署 secret 不可混用。接收端保留原始请求字节，验证时间戳格式和时间窗，以 HMAC-SHA256 校验 `timestamp + "." + 原始正文`，恒定时间比较 `X-Upaynow-Signature`；核对 `X-Upaynow-Event` 与正文事件 ID 一致，并检查正文事件类型是否属于双方约定的事件。

**在哪里点击填写：** 进入“付款通知”，核对订单、事件、状态、尝试次数和下次尝试。服务自动最多尝试 8 次；接收端恢复可用后，对“待发送”或“发送失败”的通知点“重新排队”。

**钱包/Gas：** HTTP 通知及重排不需钱包、不花 gas。

**成功看到什么：** “已送达”仅表示接收端返回 2xx，不等于已经发货。商城应先可靠入库，再返回 2xx；按事件 ID 去重、按 stateVersion 防旧覆盖，复核订单号、部署、链、Factory、CA 和原始数量，必要时服务器查单确认 paid 与 syncHealthy 均为 true，再用数据库事务/唯一约束做订单级履约幂等。

**异常：** 重排事件 ID 不变，时间戳和签名可变化，不得重复发货。链重组可先产生 payment.reversed、再产生新一轮 payment.paid；撤回时停止未执行履约并人工对账，已发商品不会自动回滚。“已作废”不应当成新待发事件；定期服务器查单对账，不能只靠回调或顾客截图。

### 3.6 用辅助工具创建测试单或补单

**适用情况：** 先验证自己的收款配置，或在核实业务情况后创建补单，不作为商城正常下单入口。

**准备：** 顶部选中正确部署，核对支持币种。首次演练建议使用测试网。

**在哪里点击填写：** 进入“设置” → “辅助工具”，展开“手动创建一笔订单”。填写“商户订单号”（如自己未用过的 TEST-0001）、“金额”，选择当前部署的“币种”和“有效期”（30 分钟、1 小时或 1 天），点击“创建订单”。创建成功会进入订单详情，再按 3.2 打开收银台。点击“清空”仅清除当前表单，不会删除已经创建的订单。

**钱包/Gas：** 创建订单本身不发链上交易。后续真的用钱包付款，付款方才需要该链 Gas；本工具不会自动替你支付。

**成功看到什么：** 提示“订单已创建”，订单属于刚才选择的部署，并有自己的收款地址和收银台链接。

**异常：** 创建前切换部署会使未提交草稿失效，应在新部署重新填写，不把原币种和金额直接带过去。创建请求超时先查相同订单号，遵守原参数幂等规则，不随意改号重复开单。辅助工具不会替商城锁库存，也不会替正式商城流程完成自动发货。

## 4. 正常归集

归集是把订单地址里指定币种的余额转入部署合约固定的 payout，不是给订单认单，也不是发货或退款。正常归集逐链、逐部署操作；不存在跨链归集队列，也没有按钱包分组的一键归集入口。

### 4.1 归集前先核对范围与费用

**适用情况：** 已收款，希望把资金移入固定收款钱包。

**准备：** 顶部“当前管理的部署”选对网络、Chain ID 和 Factory，核对“收款钱包”。同一链多套 Factory 也要分别处理；切部署后原选择会清空。看顶部同步状态，异常时先排查，不把离线旧数据当最新余额。准备兼容钱包和这条链的原生币支付 gas；持有订单代币不等于有 gas。

**在哪里点击填写：** 进入“归集”，确认有“可归集 / 异常恢复 / 归集记录”三个页签。正常路径不填任意收款地址、不改 payout，也不填私钥、助记词。只选择需要归集的订单和发送钱包。

**钱包/Gas：** 发送归集交易的钱包支付当前链原生币 gas；固定收款钱包是资金去向，二者不必相同。正常归集合约允许其他人付 gas 调用，资金仍只进固定 payout，不要求必须用 payout 钱包签名；不要把部署或错链找回的签名限制照搬到这里。后台不保管私钥。

**成功看到什么：** 当前部署、链、资金去向与商户记录一致，钱包网络正确，有可用 gas。归集调用目标是 Factory，而资金最终到固定 payout，这两个地址不同属正常情况。

**异常：** 无 gas、网络/账户变化、部署未核验、同步追赶中，先停止确认并排查。不要往每个订单地址充值 gas；本流程由发送钱包支付手续费。手机入口、WalletConnect 均不是改变资金去向的办法。

### 4.2 单笔、所选批量与全部已付足

**适用情况：** 单笔结算、选几笔对账，或统一清理当前部署已付足订单。

**准备：** 正常优先处理 PAID/OVERPAID。提前核实超额、迟付与客户纠纷，归集不会自动退款，也不会只取应付金额。

**在哪里点击填写：** 任选一条路径：

1. **单笔：** “订单”点订单行，在详情底部点“归集此订单”。该按钮要求已付足、未显示已归集，且没有进行中的交易。
2. **所选批量：** 在“订单”列表勾选左侧复选框，点“归集所选 N 笔”。建议先筛“已付足”，再逐笔检查；这是手动指定范围，不应误认为自动排除了所有欠款或迟付。筛选变更后也要核对最终所选数量，不把隐藏选择带入本批。
3. **全部已付足：** “归集 → 可归集”点“核对可归集订单”。后台先同步，再读实时余额，不发交易。预览对照“商户订单号 / 应付 / 当前余额（将全部归集）”和固定收款钱包；超过 2 分钟需点“重新核对”。确认后点“归集这 N 笔”。

三条路径进入“发起归集”，核对网络、资金去向、订单数、币种，再选择钱包方式。全部已付足的后端条件是已确认足额、无活动锁且该 CA 当前余额非零；已明确接受的足额迟付也可进入，因此不能只按页面“有效期内”的简述判断。准备时会再检查，预览数量不保证等于最终任务数量。

**钱包/Gas：** 勾选、同步、核对和打开弹窗不花链上 gas；交给钱包并广播后才进入链上费用流程。这里的“确认”是批准本批归集，不是另有一笔 ERC-20 approve 授权教程。

**成功看到什么：** 预览余额与预期相符，汇总包含正确部署、本批范围和固定 payout。执行时会归集该币种的全部当前余额，含超额及预览后新到账；预览是快照，不锁定转账金额。

**异常：** “没有可归集的订单”可能是尚未确认、余额已归集或订单被未决任务锁定；先查订单和“异常恢复”。失败读取不是零余额。欠款/迟付需人工业务判断，不能用手动批量强行替代认单。其他支持币、错币/原生币和错链找回属于另行核实的例外，不混入正常流程。

### 4.3 在电脑钱包确认

**适用情况：** 使用本机扩展钱包，或用 WalletConnect 连接钱包。

**准备：** 本机安装兼容 EIP-1193 的钱包扩展。只有选择 WalletConnect 时，才需在“设置 → WalletConnect → Reown Project ID”填自己申请的 32 位十六进制 ID 并点“保存”；此项可留空，本机扩展和手机专用扫码不需要它。不要把 API 凭据或钱包私钥填到这里。

**在哪里点击填写：** “发起归集”点“本机浏览器钱包”或“WalletConnect”。完成账户连接、网络切换；WalletConnect 按其连接弹窗扫码授权。出现“核对并确认归集”后，复核网络、发送钱包、固定收款钱包、Factory、订单数、记录 ID。点“确认并交给钱包”，再在钱包自己的交易确认界面核对网络、合约和手续费，确认发送一次。

**钱包/Gas：** 由所连接账户承担 gas；归集交易 value 为零不表示没有手续费。钱包可要求切链或添加网络，须核对 Chain ID。全过程无需导出私钥。

**成功看到什么：** 钱包返回哈希后，后台登记并核验。弹窗提示“已登记原交易哈希，等待后台链上核验”只是等待状态；提示已上链仍须去“归集记录”看逐笔结果。

**异常：** 点击前可“取消”；开始后断网、关窗或账户变化不会撤回已发交易。若出现准备记录但未发送，可去恢复页核实后取消；若结果未知，不重新点整批发送，按 4.6 恢复原任务。

### 4.4 用手机钱包扫码确认

**适用情况：** 电脑选定订单，手机钱包支付 gas。

**准备：** 手机钱包具有内置浏览器，准备当前链 gas。设置中的“手机入口”需可用；默认临时模式最长开放 5 分钟。固定 HTTPS 配置也存在，以本实例设置为准，不将它说成永久后台授权。

**在哪里点击填写：** “发起归集”点“手机钱包扫码”，等待临时 HTTPS 入口和二维码准备完成。用手机钱包内置浏览器扫码；手机页面核对“网络”“资金去向（固定）”“gas”“本批订单”。依次点“连接钱包 → 核对交易 → 确认归集并支付 gas”，再在手机钱包确认交易。不要拿顾客收银台二维码当归集入口。

电脑可点“作废入口”撤销票据并关闭通道；“收起（入口保持到期）”只是收起，不是撤销。归集页“手机归集入口”的“立即关闭”关闭当前临时通道，不取消已发送交易。

**钱包/Gas：** 手机连接的钱包支付这条链原生币 gas，后台仍不接触私钥。手机归集二维码不是 WalletConnect 配对码，无需 Reown Project ID。

**成功看到什么：** 手机显示已提交/归集完成或部分失败，电脑刷新可查同一任务和原哈希。返回电脑“归集记录”逐笔核实；到期只是入口失效，不代表交易失败。

**异常：** 启动入口失败且尚未进入发送时可改用本机钱包；一旦开始钱包确认，先查原任务。链接/二维码是本批短期能力授权，持有人能查看并尝试执行本批，不能公开分享截图、完整链接或浏览器存储；它不提供管理登录权限。共享设备用后先作废入口，再关闭该标签页；不要只依赖关闭页面撤销权限。短期权限也无法撤回已下载调用数据或已广播交易。

### 4.5 核验每项结果，而不只看批次上链

**适用情况：** 钱包已返回哈希或后台显示已上链。

**准备：** 保留部署、任务 ID、哈希和本批订单记录。

**在哪里点击填写：** “归集 → 归集记录”找到本批，核对“结果”“订单”“交易”，展开“逐笔结果”；再回订单详情看“归集记录”。链上外层交易成功不能代替逐项检查。

**钱包/Gas：** 查看免费；交易回滚仍可能消耗 gas，不能把未转出资金理解成没收手续费。

**成功看到什么：** “已上链 · 全部成功”还应结合逐笔 Collected 和固定 payout 实际到账核对；带转账税或特殊逻辑的代币，其事件报告金额不等于钱包净到账保证。“已上链 · 部分失败”须找出 CollectFailed 对应订单与原因码。订单“已归集”“归集失败”“已执行 · 无余额”有不同含义，无余额不等于本次成功转出应付金额。

**异常：** 部分失败时资金仍在对应订单地址，查明原因并重新读余额后，仅处理需要重试的部分；不要把整批按未执行重复发送。归集成功不更新库存，不代表订单支付足额或通知已经送达。

### 4.6 拒签、UNKNOWN 与手动恢复

**适用情况：** 等不到哈希、页面断线、手机到期，或 RPC 长期不给回执。

**准备：** 先保留原任务，去发送钱包及正确链区块浏览器查原交易。后端在交给钱包前就会持久化 UNKNOWN；它既不是失败证明，也不是已经广播的证明。

**在哪里点击填写：** “归集 → 异常恢复”按证据处理：

- 有原哈希：点“登记原交易哈希”，填 0x 加 64 位十六进制，点“登记并核对”，再“刷新状态”。它只登记、不重发，后台核对链、发送者、Factory 与调用数据；本机若有暂存哈希，可点“重试登记本机原哈希”。
- 明确未开始的 PREPARED：在可用时点“取消未发送的准备记录”，再重新核对。
- 钱包明确拒绝且确认无哈希：符合条件时点“登记明确拒签”，按两次确认完成。超时/断网不是拒签；登记后仍观察约 64 个区块，迟到原交易可能被识别。
- 手机若出现“重新请求钱包确认”，这是恢复同一批准任务的显式功能，不是自动重发保证。先排除原钱包仍有待确认请求或已有交易；有哈希就登记，不另建批次、不同时确认旧新请求。迟到哈希仍可能返回，应保留全部钱包证据。
- 无法自动核实时，最后才用“人工更改状态”：选择人工成功、失败/未执行或未核实结案，填至少 4 字依据并勾选风险确认，点“确认更改”。

**钱包/Gas：** 登记、刷新、人工结案不发新交易、不花 gas；重新请求钱包并再次确认则可能产生交易和手续费。

**成功看到什么：** 原哈希登记后进入核验，最终看真实逐项回执。人工结果会明确显示人工备注，不等于后台已验证链上成功；原记录和哈希保留。

**异常：** 人工结果解除本任务订单锁，不改付款状态，当前实现也停止该任务自动观察、自动刷新不会覆盖人工结果。不能笼统承诺所有“结案”都继续观察：拒签观察与人工更改不同。若原交易仍执行，解锁后重发可能重复消耗 gas；证据不足宁可保留 UNKNOWN 并对账。未决任务只锁其涉及订单，不必把整个部署或其他链停掉。

## 5. 错币与错链找回

### 5.1 先确认资产在哪里，再选择操作

找回不是补记付款。正常付款必须是订单指定链、指定代币 CA、指定订单地址，并满足金额、确认数和有效期规则。归集成功也不代表订单支付成功。请先保留原订单、顾客交易哈希、实际 Chain ID、接收地址、资产合约地址（CA）、原始数量及区块浏览器链接，不要让顾客为了“激活找回”再转一笔钱。

先在实际转入链查询交易是否成功，核对完整接收地址；再查该地址的准确 CA 余额或原生币余额，同时确认固定收款钱包和目标部署。币名、图标、钱包估值、顾客截图都不能证明 CA 正确。未支持代币和原生币不会由正常付款扫描完整列出；订单页没显示，不等于链上没有。恶意代币也可能虚报余额。

| 实际情况 | 当前处理判定 | 付款状态与限制 |
|---|---|---|
| 正确链、正确订单地址，但转错代币 | 已在本部署支持列表中，用“归集其他支持币”；不在列表中，用“归集错币 / 原生币” | 不改变订单币种、不合并抵扣订单应付 |
| 正确链、正确订单地址，转入 ETH、BNB 等原生币 | 在错币入口填零地址，手动归集 | 原生币不是本订单指定 ERC-20，不算付款 |
| 错误链、与原订单文字相同的地址 | 只有符合下述 deterministic-v2 同址条件，才可使用“错链找回” | legacy 不因升级软件而获得 v2 找回能力；不能承诺成功 |
| 完全转错地址 | 本系统不能任意提取他人地址资产；联系实际控制者或平台 | 没有万能找回、撤销转账或改目的地功能 |
| 代币冻结、黑名单、禁止转账或恶意合约 | 可能读到余额但无法转出；先联系发行方核实限制 | 本系统不能解冻，反复发送可能仅消耗 Gas |

### 5.2 正确链上的错币、其他支持币与原生币

**适用情况 →** 资金确实在当前部署链的原订单地址。可找回并不要求把订单改为已付；不要重新开单试图取得相同地址。

**准备 →** 登录后选择正确部署，打开对应订单详情，核对链、订单地址、固定收款钱包和资产 CA；在区块浏览器或可信只读工具查余额。先判定资产是否属于该部署支持列表，而不是只看它是否是订单付款币。若订单已有进行中的归集任务，先按第6章核对原交易。

**点击／填写 →** 展开订单详情“高级”：

- 已支持但不是本单付款币：点击“归集其他支持币”，从“币种”选择准确代币，再点“下一步”。
- 未支持代币：点击“归集错币 / 原生币”，填写完整“代币合约地址”。核实后才勾选“我确认要调用这个合约，并理解它报告的余额不一定可信。”，再点“下一步”。
- 原生币：同一入口填写 `0x0000000000000000000000000000000000000000`，不是包装币 CA。WETH 等包装币仍须填自身合约地址。

“归集错币 / 原生币”弹窗本身没有“先查询余额”按钮；请先完成外部只读核实，不能把它写成自动识币工具。后台要求显式错币确认，支持列表中的资产不能走错币合约调用，需返回选择正确入口。

**签名／Gas →** 在“发起归集”选择“手机钱包扫码”“本机浏览器钱包”或“WalletConnect”；后者需自己的 Reown Project ID。核对摘要中的网络和固定收款钱包。本机流程会再显示“核对并确认归集”，点击“确认并交给钱包”后才由钱包发送；手机按手机页明确确认。连接账户、查询和准备不是转账。Gas 由发送钱包持有该链原生币支付，不是由订单余额自动代付；准备阶段有估算，不保证最终一定成功。

**结果 →** 合约将执行时该币种的全部可转余额直接归集到本部署固定 payout，不能在这里填写顾客退款地址或指定部分金额。检查“归集 → 归集记录”、交易回执，以及 payout 实际到账。收税代币、恶意余额报告可能使事件数量不等于净到账，不能只凭显示金额结账。这些手动处理不改变原订单的付款币种，也不会把错币当支付成功。

**异常 →** 地址格式错误、误把支持币填入错币入口、余额读取或估算失败时，停止并重新核实。原生币转出也可能因 payout 拒收而失败。手机入口失败可改用本机钱包；关闭二维码、断网或通道到期均不能撤销已发出的交易。若结果未知，先找原哈希，不要马上再归集。

### 5.3 错链同址找回：必须同时满足的条件

1. 来源和目标都是已登记且可用的 `deterministic-v2` 部署，Chain ID 不同；payout、Factory、确定性 deployer 相匹配。
2. 保存并使用**原订单 orderHash**，不能另开订单、换 UUID 或凭订单号重新造 hash。系统会比较两链 implementation、预测订单地址和来源保存地址。
3. 两链须具有兼容的固定版本、编译字节码与地址推导方式；系统核验官方 ERC-2470 入口运行时代码、固定 deployer、Factory／implementation 字节码和不可变字段、代币注册表。只添加 RPC、同为 EVM 或显示相同地址都不是证明；链还需支持当前合约指令。
4. **目标商户部署已完成并核验**。公共入口就绪不代表商户 Factory 已部署；没有匹配目标时先去“链与合约”完成合法部署／导入。当前新商户部署只对已开放网络提供；不要求普通商户手动广播公共入口交易来绕过限制。
5. 目标链准确 CA 确有可转余额；代币未冻结、不阻断转出。目标固定 payout 须能由当前钱包实际控制并签名，且有足够目标链 Gas。智能合约钱包同一个文字地址不证明另一链上的控制权相同；交易所充值地址通常不适合此模式，不能假定都兼容。

legacy 订单没有上述承诺；已有 Factory 不可升级。新建 v2 部署只影响新部署／新订单，不能重写旧订单归属来“升级找回”。

### 5.4 使用已实现的“错链找回”界面

**适用情况 →** 符合上一节全部条件的错链同址资产，且来源订单记录仍在。

**准备 →** 在来源部署打开原订单详情，确认目标部署已登记，备妥目标链 CA；原生币仍用零地址。确保目标 payout 钱包在手、网络可用。

**点击／填写 →** 点击订单详情底部“错链找回”。没有匹配目标时，界面会提示“没有匹配的目标链部署”，不是自动跨链部署。在“目标链（已注册的同地址部署）”选择实际转入链，填写“目标链资产 CA（原生币填零地址）”，点“只读查询并核对”。核对原订单、目标链、同一订单地址、资产 CA、余额、固定收款钱包。精度无法读取时余额按原始单位显示，不能把它当正常人类单位。余额大于零才显示后续连接入口。

**签名／Gas →** 点击“连接本机钱包并核对找回”，或“WalletConnect”；当前不支持错链找回专用手机二维码流程。使用目标部署固定 payout 钱包，核对目标链与 Factory，再点“确认并交给钱包”，由钱包明确确认并支付目标链 Gas。此过程会重新查询与校验，锁定原订单和目标部署；过程中切换管理部署、钱包账户或网络会阻止发送，不要靠切换网络纠错，关闭后重新核对。

**结果 →** 资金仍在**目标链**，只被收回到该链固定 payout。这不是桥接回来源链，不是自动退给顾客，不创建新发票，不把来源订单改成 paid，也不因找回触发来源订单付款成功通知。退款或账务抵扣由商户另行核对决定；顾客订单如何履约应独立处理。

**异常 →** 零余额、部署不匹配、字节码／入口校验不通过、签名账户不是 payout、Gas 不足或代币拒转时，不应继续强发。已有 UNKNOWN 或已登记哈希时，切换到**目标部署**的“归集 → 异常恢复”，登记并刷新原交易，勿在来源部署重建任务。保留任务 ID、原哈希、目标 CA 与核实记录供排障。

## 6. 异常处理与日常维护

### 6.1 顾客已转账，订单仍未付款

**适用情况 →** WAITING、PARTIAL、CONFIRMING、EXPIRED、LATE_PAYMENT，或顾客截图与后台不一致。

**准备 →** 取得原订单、真实交易哈希、Chain ID、完整接收地址、CA、数量及时间。检查实际交易回执，不能只看“钱包扣款”。付款与归集是两套状态：余额已被归集不等于付款记录消失；归集未做也不妨碍正确付款被确认。

**点击／填写 →** 选对部署并打开订单详情，核对指定币种、金额、到账记录、有效期和付款确认数。CONFIRMING 等确认；PARTIAL 查是否不足额；过期后到账不会自动成为正常付款。已确认且合计付足的迟付，须按订单迟付处理流程由商户明确接纳，不能通过归集错币补记。错链／错币转第5章；不要修改数据库中的 paid。

**签名／Gas →** 查单、扫描、核对付款不需要钱包签名或 Gas；不要把再次付款当排障步骤。

**结果 →** 只有指定链上指定付款 CA 的合格到账达到应付并满足确认规则，才产生付款状态变更。余额查询不替代付款账本；正常扫描只查询部署支持列表内的 Transfer 日志，不能承诺识别所有错币或原生币。

**异常 →** 如概览提示“链上同步异常”，由部署者检查该链 RPC、扫描游标与最新区块、最近同步、错误码。`/health` 的 ok 仅证明进程活着，不证明付款扫描健康。深度重组超出保留检查点会报 `DEEP_REORG_MANUAL_RESCAN_REQUIRED`，须保留数据请维护者制定重扫方案，不能随意清游标、删订单或伪造付款成功。

### 6.2 付款已确认，商城没有收到通知

**适用情况 →** 后台已付但商城未更新，或“付款通知”出现待发送／失败。

**准备 →** 确认下单时填写了 webhookUrl，拿到对应部署及事件 ID。部署者检查商城 HTTPS、DNS、TLS、接收路由、`UPAY_WEBHOOK_HOSTS` 精确主机白名单和对应部署的通知验签密钥；不得把生产回调改成本地地址绕过安全限制。

**点击／填写 →** 打开“付款通知”，核对订单、事件、尝试次数和状态。修复接收端后，对 PENDING／FAILED 记录点“重新排队”。该操作保留原事件 ID，重置重试计数，并非已经送达；已送达记录没有这个重排按钮。

**签名／Gas →** 后台签名 HTTP 通知，不需要链上钱包或 Gas。商城须使用该部署的 `webhook.secret` 校验时间戳与原始请求体签名；这不是登录密码、恢复密钥或 API 凭据。

**结果 →** 自动重试最多 8 次后进入 FAILED；“已送达”仅表示商城返回 2xx，不等于已发货。商城按事件 ID 去重并查单、幂等履约；链重组可能产生撤回及新的付款确认，不能每条通知都发一次货。

**异常 →** 网络超时也可能发生在商城已处理之后，故重新排队仍可能重复抵达。不要删除通知表、重造事件或批量再下单。恢复旧备份也可能再次投递旧事件，先与商城对账。

### 6.3 RPC、钱包断线与 UNKNOWN

**适用情况 →** 同步异常、上游错误、钱包已弹出但无结果，或归集显示 UNKNOWN／SUBMITTED。

**准备 →** 记录部署 ID、任务 ID、钱包账户、网络、原哈希及错误码。部署者检查 HTTPS RPC 可达性、限流和真实 Chain ID，不能靠改网络名称蒙混校验。界面未提供任意在线改写现有部署 RPC 的通用修复按钮；具体服务器配置修复由部署者按已部署版本处理，不能直接改 SQLite。

**点击／填写 →** 在“归集 → 异常恢复”先点“刷新状态”。没有哈希时去发送钱包或浏览器查原交易，再点“登记原交易哈希”→填写 0x 开头完整哈希→“登记并核对”。后台匹配发送者、Factory、调用数据和网络，不是填任何到账哈希都能结案。若本机保留了待登记数据，可使用“重试登记本机原哈希”等实际出现的恢复按钮；这是登记，不是重发。

仅 PREPARED 未交给钱包时可“取消未发送的准备记录”。只有钱包明确拒绝且确认未发出时，才使用“登记明确拒签”，完成两次确认；后台还观察约 64 个区块。超时、断网、关闭页面、临时通道到期都不是拒签证据。

**签名／Gas →** 刷新、登记、拒签声明或人工结案不发送新交易、不付 Gas；它们也不能撤销已经签名／广播的交易。先找原交易，勿为解除锁重复签名。

**结果 →** 节点恢复连接后，后端会继续查原交易。确认成功后看逐笔结果；确认整笔交易回滚后才考虑重新归集。没查到交易或确认数不足，不代表已经失败，系统不会自动重发。批量交易成功不代表逐笔成功；请查看“归集记录”的“逐笔结果”，特别是 CollectFailed 与 payout 净到账。UNKNOWN 只暂停关联订单的归集，余额并没有被冻结，也不影响其他订单。

**异常 →** 长期无法从 RPC 获得可靠结果时，可在自行核对钱包、区块浏览器及到账后点“人工更改状态”，选择“人工确认成功”“人工确认失败 / 未执行”或“仅人工结案，结果仍未核实”，填写至少 4 字依据、勾选风险确认再“确认更改”。它仅记录人工结果并解除任务锁，**不是链上验证，不改订单付款状态**；源码会停止该任务的自动观察，不能承诺以后自动纠正人工结果。保留哈希、证据和历史，谨慎决定能否再次发起。

### 6.4 修改密码与忘记密码

**适用情况 →** 日常换密或无法登录；不是找回钱包私钥。

**准备 →** 当前密码或本实例有效恢复密钥。若密钥遗失，先按 1.2 核对真实数据根目录。支持系统剪贴板的 Mac/Windows 可在项目根目录使用 `npm run recovery-key -- --copy "/实际数据根目录"`；无桌面剪贴板的 Linux 服务器使用 `npm run recovery-key -- "/实际数据根目录"`，仅在受控终端查看并安全保存，禁止把明文放进日志、录屏或工单。不要对不确定的数据目录直接执行。

**点击／填写 →** 已登录：“设置”→“修改密码”，填当前密码、新密码、确认新密码，点“修改密码并退出”。忘记密码：登录页“忘记密码”，填“现有恢复密钥”、新密码和确认，点“设置密码并生成新恢复密钥”。新密码 12–128 字符，不能全空白或直接复用其他凭据；首尾空格保留。保存新恢复密钥后勾选确认，再“已保存，返回密码登录”。

**签名／Gas →** 无钱包签名、无 Gas。

**结果 →** 改密和重置均令全部浏览器会话失效，需重新登录；只有重置还轮换恢复密钥，旧密钥立即失效。独立 API 凭据不受这两种操作影响。日常可在“设置”→“备份恢复密钥”，再次验证当前密码后复制／下载；这不是完整数据备份。

**异常 →** 重置响应丢失时先尝试新密码登录再取回新密钥，或由部署者用本机工具读取。AUTH_RATE_LIMIT 时停止连续尝试；认证文件损坏、存储错误须保留现场。禁止删除 auth.json“恢复登录”：这可能生成另一套身份并破坏商城凭据一致性；改密也不能补救泄露的 API 凭据。

### 6.5 完整一致性备份与安全恢复

以下没有“一键备份／恢复”管理按钮，由有权部署者在服务器执行。

**适用情况 →** 日常备份、迁移、升级前或故障恢复。

**准备 →** 从实际启动参数和进程环境确认数据根目录：程序选项 dir 优先，否则 `UPAY_DATA_DIR`，未设才回落项目的 `backend/state`。备份根目录全部内容，包括 auth.json、根数据库、部署注册信息、全部 `deployments/<uuid>/`、各部署数据库、`webhook.secret`、其他密钥、订单、扫描检查点、通知及 UNKNOWN／部署任务。另安全记录程序版本、依赖锁文件（package-lock.json）、合约构建产物／固定版本清单和实际运行环境配置。`.env.example` 只是说明；单独编辑 `.env` 不会自动进入服务进程。

**点击／填写（服务器操作）→** 优先安排维护窗口，由部署者正常停服、确认所有写入者结束后做完整快照。在线备份必须使用 SQLite backup 等一致机制，并使根注册表、所有子库及认证／密钥处于相容时间点；逐文件热复制不等于全实例一致快照。SQLite 开启 WAL：不能只拿 merchant.sqlite，忽略尚有事务的 `-wal`／`-shm`；也不要手动删除这些文件来“修复”。备份加密、限制访问，记录时间与版本，做隔离恢复演练。

**签名／Gas →** 备份恢复无链上签名与 Gas；但备份含管理与通知秘密，按资金相关敏感资料保护。

**结果 →** 恢复前保全故障现场和现有数据，在受控目录恢复完整同一批快照，核查权限、版本、所有部署及密钥对应关系。先在不向生产商城发通知的隔离环境校验数据库完整性和记录；演练副本禁止访问生产回调地址，不与原实例共用数据目录；接生产前核查新旧时间差、链上原交易与商城已履约记录。保留原 Factory、payout、订单 hash、未知任务，不能让旧订单指向新合约。

**异常 →** owner.lock 是占用保护，不是废文件。出现 STATE_DIRECTORY_LOCKED，先查持有进程、PID 与实际目录；仅确认崩溃且无任何写入者后才由部署者处理遗留锁。不要删认证、锁或任务表“清障”。恢复成功不等于钱包和链状态回到备份时刻，备份后的链上交易仍可能已经生效。

### 6.6 升级、回滚、迁移与求助

**适用情况 →** 更新版本、更换服务器或提交无法自行解决的问题。

**准备 →** 取得经过授权核验的当前发布来源，不能照旧安装文档中的历史 repository 地址直接覆盖生产。备份代码版本、构建产物、依赖锁、完整状态和实际环境；确认 Node／SQLite、数据库格式及合约固定版本兼容。

**点击／填写（服务器操作）→** 由部署者按实际进程管理方式安排切换。新版本先用隔离副本验证，不把旧程序直接打开新格式生产数据库作为“回滚”；必要时恢复匹配旧版本的升级前一致快照，并核对期间新订单、交易和已发通知。迁移前结束旧实例写入；禁止两个实例同时写同一目录，也要避免两个不同目录的副本同时扫描同一业务并双重通知。

**签名／Gas →** 软件维护不要求钱包签名；软件升级不会升级不可变链上合约。如要求重新部署，应作为独立资金操作重新审核。

**结果 →** 上线后逐部署核对 Factory／payout、订单数量、同步、通知与 UNKNOWN；确认商城幂等和签名密钥正确再恢复业务。证书续期、磁盘空间、受保护备份和恢复演练由部署者日常负责。

**异常 →** 手机临时入口不能用时，当前实现会优先使用显式配置／系统 cloudflared；缺少时在支持的平台按需从官方固定发行源下载并校验，非默认要求先手装。普通启动不下载或自动开放公网；显式路径无效、校验失败、下载失败、缓存权限或平台不支持须按错误处理，不能关闭校验；固定 HTTPS 模式不需要该组件。求助仅提供版本、部署 ID、Chain ID、错误码、脱敏日志及必要交易哈希／CA；遮掉密码、恢复密钥、API 凭据、Cookie、通知密钥、RPC URL 中的 token、二维码及临时入口链接。

求助入口沿用 README 的“问题反馈与联系”。安全问题先私下联系，不在公开帖子贴敏感数据；公开交易哈希、地址和部署信息也只提供排障所必需的部分。

## 附录：常用名词速查

| 名词 | 在本手册中的含义 |
| --- | --- |
| 网络 / 链 | 资产实际所在的网络。不同网络上的同名币不是同一笔余额 |
| Chain ID | 区分 EVM 网络的数字标识；不是商户部署 ID |
| RPC | UPayNow 与链通信使用的节点服务。普通商户选网络后使用系统预设，只有确需换节点才用高级设置 |
| CA | 代币合约地址；识别代币要核对网络和完整 CA，不能只看名称或图标 |
| Factory | 商户收款合约，固定绑定收款钱包与支持币种，用于管理对应的订单收款地址 |
| payout | 合约固定的最终收款钱包；不是顾客每笔订单需要转账的订单地址 |
| 部署 ID / deploymentId | 后台区分一套商户部署的标识；商城开单必须使用正确部署的 ID，不可拿 Chain ID 代替 |
| 订单地址 | 分配给某笔订单的付款地址。顾客应付至收银台显示的订单地址，而不是随便转入 Factory 或 payout |
| orderIdHash / orderHash | 用于推导订单地址的原订单身份哈希；不是顾客付款交易哈希，错链找回不能随意新建替代 |
| 交易哈希 / txHash | 某笔链上交易的标识。顾客付款、商户部署、归集是不同交易，登记恢复时不能混用其哈希 |
| Gas | 链上交易费用，由发交易的签名钱包支付，需准备交易实际所在链的原生币 |
| Webhook / 付款通知 | UPayNow 向商城发送的带签名 HTTP 通知；通知密钥与 API 凭据不同，已送达不等于已发货 |
| UNKNOWN / 结果未知 | 无法确定原交易的最终结果；不是失败，不能据此盲目再次发送 |
